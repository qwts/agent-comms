# Owner decisions: proposed locking and crash evidence

This is part of the proposed [effect evidence contract](owner-decision-effect-evidence.md), not a runtime claim. It preserves existing owner gates and local command behavior while defining the reviewed internal adapter requirements.

## Lock and crash rules

The daemon's asynchronous per-soul coordinator performs all broker checks/native work before locks. Under the local journal lock, acquire the domain locks in one declared order; no await and no nested call to public lock-acquiring APIs. The reviewed candidate order is request-journal → lifecycle(soul) → revision(soul) OR cold-settings(global) → webhook(soul) → tool-home(soul) → wake-sessions(global) → population(global). A transaction takes only its domain branch and required later locks. No identity mutation occurs under these locks; the active-identity read is read-only. Lifecycle participation closes retirement between active check and mutation; local behavior/gates remain unchanged.

The [source lock graph](#current-lock-graph-and-required-cutover) is the basis for this order, not a claim that adding the last lock is automatically safe. New cores expose internal lock-held helpers; public lock-acquiring operations are never nested. Journal writes use reserved capacity and never reacquire a journal lock inside a domain callback. No async authorization/network/prompt/process execution occurs under the locks; existing synchronous identity reads must be factored into a verified read-only mechanism before the final adapter can claim this constraint.

Revision append and fsync are already a core seam in PR986. Working-file application is still per-file; add file+directory flush/readback before completed, with request-linked entered durable first. This does not claim whole-folder atomicity. All cold settings/save/remove writers need one shared synchronous core, plus common readers selecting coherent settings+webhook state. Today removeWebhook is unlocked and webhook CLI saves before settings; enabling the adapter while retaining those seams would be incorrect. Readers encountering an unfinished entered cold effect fail closed for that soul, rather than consume a partial settings/secret pair. Immutable pending/completed records can be inspected under domain locks without reversing lock order.

Crash before entered and with a durable pre-effect refusal: refused. Crash after entered but before proof of the requested entire effect: indeterminate, never auto-retry/repair. For approve/reject/adopt/edit(false), the explicit owner-local reconciliation ceremony may produce a missing typed completed record from the original retained entered record plus the validated request-linked authoritative revision/decision event and immutable package, after resync and matching actual-state verification. This only records evidence of the already completed semantic mutation; it performs no effect/repair. Its completed detail links journalSeq/journalRecordDigest exactly as normal completion, then reconciliation basisDigest references that completed evidence. No automatic recovery does this. For edit(true) and cold wake, such an event alone is insufficient; they require whole-effect completed evidence. For edit(true), a linked head alone is insufficient. For cold, a matching preexisting resulting value is insufficient. Complete evidence must be request-linked, validated, and match actual current state for reconciliation; unknown concurrent changes retain indeterminate. A complete record that may have been published but failed directory fsync is uncertain until recovery validates it and durably preserves it; no success is acknowledged on the failed original call.

This graph supports the candidate order but is not implementation proof: cross-process races, lock timeout/live-owner handling, fsync failure, state-file size limits and quarantine behavior require focused adversarial tests before enabling any domain. The bounded companion vectors are specification evidence, not conformance claims. The bot's existing directory durability is POSIX-only; Windows must not advertise this adapter until equivalent reviewed flush evidence exists. No broader owner policy gate is introduced by these routine typed records/numeric budgets.
